# Fieldtest

## Zweck & Links

- Tester-Service für Prototypen: Overlay im Prototyp, Belohnung in Sats, Feedback mit Ort in der App. Ausgezahlt wird über den Runner des Owners (`apps/runner`).
- Live: https://fieldtest.pleasance.org, Coolify-Projekt `pleasance-fieldtest`, Ressource `fieldtest` (web, api, worker, postgres).

## Checks

`bun run check && bun run test` (`test` baut das Web und testet den Build). Die Browser-Tests starten API und Web auf eigenen Ports (31100, 31101), unter dem ephemeren Linux-Portbereich (32768–60999), damit ausgehende Verbindungen sie nicht kurzzeitig belegen. Testet ein anderer Worktree gleichzeitig, mit anderen Ports unter 32768 aufrufen: `TEST_API_PORT=31102 TEST_WEB_PORT=31103 bun run test`.

## Deploy

- Ein Push auf `main` baut nach grüner CI die Images und deployt sie über die Coolify-API (Secrets `COOLIFY_TOKEN` mit dem Token `ci-fieldtest` und `COOLIFY_UUID`). Ohne `COOLIFY_TOKEN` überspringt die CI den Deploy.
- Prüfen: `gh run watch`. Mit Deploy ist der Job erst grün, wenn `https://fieldtest.pleasance.org/api/health` (bzw. die Repo-Variable `API_URL`) den Commit als `revision` meldet.

## Fallen

- Secret-Scan: Gitleaks 8.30.1 liest zusätzlich zu `--gitleaks-ignore-path` auch `.gitleaksignore` aus dem Checkout. Der Workflow ersetzt diese Datei deshalb ebenfalls durch die Fassung aus `CONFIG_REF`, bei Fork-PRs also aus dem Base-Commit.
- Fieldtest verwahrt nie Geld: keine Guthaben, keine Wallet-Secrets der Owner auf dem Server, keine eigene Cashu-Mint, kein Tausch. Ausgezahlt wird nur über den Runner des Owners. Sonst wäre eine MiCA-Erlaubnis nötig.
- Live-Belohnungen berechnet die API (`lib/sessions.ts`), dem Overlay wird nichts geglaubt außer „aktiv in diesem 10-Sekunden-Fenster“, und auch das nur bis zur verstrichenen Zeit.
- Geldbeträge in Sats als ganze Zahlen, Reputation und Skalierung in Prozent.
- Finding-Belohnungen rechnet `settleFinding` in `lib/claims.ts` in einer Transaktion unter der Zeilensperre der Runde ab (`for no key update` auf `rounds`, wie die Finding-Nummern in `routes/sdk.ts`). Owner und Worker bewerten dasselbe Finding sonst gleichzeitig und hinterlassen doppelte Claims. Wer Claims eines Findings schreibt, tut das in dieser Transaktion, nicht daneben.
- Das Overlay (`packages/sdk`) läuft in fremden Prototypen: Shadow DOM, keine Abhängigkeiten, jede eingesetzte Zeichenkette über `esc()`.

## Konventionen

Stack und Aufbau: siehe README.md. Gestaltung: siehe DESIGN.md.

- Neue Tabelle: `packages/db/src/schema.ts` ändern, `bun run db:generate`. Die Migration läuft beim nächsten API-Start, `migrateDb` lässt mehrere Instanzen nacheinander migrieren. Jede Migration muss mit dem noch laufenden alten Code funktionieren: Spalten nullable oder mit Default hinzufügen, Umbenennen und Löschen erst im Deploy danach. Nichts von Hand in der Datenbank ändern.
- Korrelierte Subselects in `sql`-Templates: Bei einem `select` aus nur einer Tabelle rendert Drizzle Spalten ohne Tabellennamen, auch im Template. `exists (select 1 from ${subs} where ${subs.userId} = ${users.id})` wird zu `where "user_id" = "id"`, `"id"` meint dann die Spalte des Subselects, das Ergebnis ist ohne Fehler falsch. Solche Subselects nur in Abfragen mit Join oder mit `alias()`, sonst zwei einfache Abfragen.
- Neue Route: Datei in `apps/api/src/routes`, in `app.ts` einhängen. `requireAuth` für eingeloggte Nutzer (danach `c.get('user')`), `validJson(schema)` mit dem Schema aus `packages/shared`.
- Fehler antworten immer als `{ error: string }` in der Sprache aus `Accept-Language`: `t(c).<key>` aus `lib/i18n.ts`, eigene zod-Meldungen sind Keys aus `messages.ts`. Das Web zeigt ihn als Toast.
- Jeder neue Text kommt auf Deutsch und Englisch in `packages/shared/src/messages.ts`, im Web über `t()` aus `$lib/i18n`. Das Tester-Overlay hat eigene Texte in `packages/sdk/src/messages.ts`.
- Alles, was Mails verschickt oder Geheimnisse prüft, bekommt ein `rateLimit` aus `lib/rate-limit.ts`. Die Zähler liegen in Postgres und gelten für alle API-Instanzen.
- Öffentliche Formulare ohne Login, die Mails verschicken oder Daten anlegen, prüfen ALTCHA (README, „ALTCHA“): `requireAltcha` vor `validJson`, im Web `Altcha.svelte` im Formular. Nicht für Links aus Mails wie Abmelden oder Login-Link und nicht für Wege mit Einladungstoken wie das Overlay der Testpersonen, die tragen schon ein Geheimnis.
- Mails über `sendMail` aus `lib/mail.ts`, im Design der Vorlage dort (DESIGN.md, „Mails“).
- Update-Mails (README, „Update-Mails“): nur mit Opt-in, Standard aus. Agenten schreiben Entwürfe als `updates/<datum>-<thema>.md` in beiden Sprachen, senden darf nur ein Admin aus `ADMIN_EMAILS` in `/admin/updates`. Kein Agent löst den Versand aus, auch nicht per API oder Datenbank. Jede Massenmail an Nutzer läuft über diesen Weg, also mit Abmeldelink und `List-Unsubscribe`.
- Registrierung geschlossen bis zu Robins Go: Neue Konten nur für Adressen in `SIGNUP_ALLOWLIST`, bestehende melden sich immer an. `SIGNUP_OPEN=true` erst nach Robins ausdrücklichem Go setzen (README, „Registrierung öffnen“). Tester lädt ein Admin aus `ADMIN_EMAILS` in der App ein (`/auth/invite`, Seite `/invite`), das öffnet nichts. Dort steht robin@pleasance.org, der menschliche Admin. admin@pleasance.org, der agentische Admin für die Savor-Vorschau, kommt nie in `ADMIN_EMAILS`, sonst legen Agenten Konten an und mailen Dritte. Wer einen weiteren Weg baut, auf dem Konten entstehen, prüft dort ebenfalls `mayLogIn` aus `lib/signup.ts`. Testpersonen einer Runde (Einladungslink, Overlay, Demo) legen keine Konten an, sondern nur Zeilen in `testers` mit ihrer Lightning-Adresse, und bleiben davon unberührt, ebenso geteilte Berichte.
- Zustandslos, damit die App ohne Umbau auf einen anderen Server umzieht oder repliziert hinter einem Load Balancer läuft (`infra.md`, „Skalierung“): Platte und Prozessspeicher halten keinen Zustand, der eine Instanz überlebt oder für alle gelten muss. Login-Sessions, Rate-Limits, Testsessions und Claims liegen in Postgres. Uploads und Medien gehen nach S3 (Hetzner Object Storage, Bucket nach Namensregel) über `Bun.s3`, das `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_ENDPOINT` und `S3_BUCKET` selbst aus der Env liest. Kein Volume außer `pgdata`. Locks per `pg_advisory_xact_lock`. Caches im Speicher nur, wenn jede Instanz sie verlieren darf (wie das gebaute Overlay in `routes/sdk.ts`), ein geteilter Cache läuft als Valkey-Container in `docker-compose.prod.yml`.
- Hintergrundjobs und Zeitpläne laufen nie im API-Prozess, sondern als eigene Rolle: Service `worker` in `docker-compose.prod.yml` aus dem API-Image mit eigenem Einstieg `apps/api/src/worker.ts`. Aufträge sind Zeilen in Postgres, der Worker holt sie mit `FOR UPDATE SKIP LOCKED`. Fällige Zeitpläne beansprucht er atomar (`update … set next_run = … where name = … and next_run <= now() returning`). Nichts in `setTimeout`, `setInterval` oder Listen im Speicher. Kurze Nacharbeit einer Anfrage wie eine Mail bleibt in der Anfrage. Im Worker laufen die Update-Mails (`deliverNext` in `lib/updates.ts`) und die KI-Bewertung (`runNextEvaluation` in `lib/evaluate.ts`) als eigene Schleifen. Zur KI-Bewertung: Die Meldung legt in derselben Transaktion eine Zeile in `evaluation_jobs` an. Ein geholter Auftrag ist 15 Minuten gesperrt (`run_at`), danach holt ihn ein Worker wieder, auch nach einem Absturz. Nach drei Versuchen bleibt das Finding beim Owner.
- Jede Rolle hat einen Healthcheck im Image: API `/api/health` (mit Datenbank), Web `/health` (nur der Prozess), ein Worker ein `/health` auf einem eigenen Port. Uptime Kuma und ein Load Balancer prüfen `/api/health` über die öffentliche Adresse.
- Jede Rolle behandelt `SIGTERM` und `SIGINT`: keine neue Arbeit annehmen, laufende Anfragen bzw. Jobs samt Transaktion abwarten, dann den Datenbank-Pool schließen. Wartepausen müssen sofort abbrechbar sein. Compose begrenzt den Shutdown auf 30 Sekunden; neue Jobs und Anfragen müssen in dieses Budget passen. Der API-Test prüft den Shutdown in echten Unterprozessen.
- Replikation und Proxy-Kette: README, „Stoppen und weitere Instanzen“. Weitere Instanzen verwenden dieselbe private Datenbank per Compose-Override, der Standard bleibt bei lokalem Postgres. `clientIp` liest den letzten `X-Forwarded-For`-Eintrag: Traefik hinter einem LB hängt dort standardmäßig die LB-IP an, auch mit `forwardedHeaders.trustedIPs`. Vor dem Betrieb echte und gefälschte Client-Header durch die gesamte Kette testen, sonst teilen sich alle Nutzer die IP-Limits. Nie ungeprüft den ersten Eintrag verwenden.
- Konfiguration nur über die Env: Jede neue Variable steht in `.env.example`, `.env.production.example` und `docker-compose.prod.yml`. Im Code keine Domains, IPs, Hostnamen oder Pfade des Servers. Service-Namen aus der Compose-Datei (`api`, `postgres`) sind erlaubt.
- Postgres hat im Compose eine Speichergrenze (`POSTGRES_MEMORY`, Standard `512m`). Wird sie eng, in Coolify erhöhen, nicht entfernen.
- Web: API-Aufrufe über `api` aus `$lib/api`, Login-Zustand aus `$lib/auth.svelte`. Seiten hinter dem Login unter `routes/(app)`.
- Externe Quellen im Browser (Skripte, Fonts, Bilder, APIs) in die CSP in `apps/web/svelte.config.js` eintragen, sonst blockt der Browser sie. Der Browser-Test in `apps/web/tests` läuft gegen den Produktions-Build und scheitert an jedem Konsolenfehler, also auch an CSP-Verstößen. Inline-`<style>` erlaubt die CSP nur im Dev-Modus: Setzt eine Bibliothek eigene Styles (etwa Web Components im Shadow-DOM), kommen deren Hashes in `style-src`.
- Link-Vorschau: Das Layout setzt die `og:`-Tags, das Bild rendert `bun run og-image` in `apps/web` (DESIGN.md, „Vorschaubild“). Danach neu rendern und committen, wenn sich `APP_NAME`, `APP_BAND`, `tagline` oder die Kachel ändern. Die Kachel liegt als `static/favicon.svg`, dieselbe wie `img/werkzeuge/fieldtest.svg` im pleasance-Repo. Öffentliche Seiten mit eigenem Inhalt geben im Server-Load `meta` mit Titel, Beschreibung und optional einem absoluten Bild-URL zurück, so wie der geteilte Bericht unter `/r/[token]`. Ungültige Links bekommen die allgemeine Vorschau. Link-Crawler führen kein JavaScript aus, also wirkt `meta` nur in `+page.server.ts` bzw. `+page.ts` auf Seiten mit SSR, nicht unter `routes/(app)` (`ssr = false`). WhatsApp speichert Vorschauen lange zwischen.
- Das Repo ist öffentlich, auch seine CI-Logs. `secrets.yml` scannt jeden Push und PR mit gitleaks (README, „Secret-Scan“). Fehlalarme eng abfangen, per Fingerprint in `.gitleaksignore` oder per Pfad und Regel in `.gitleaks.toml`, nie eine Regel ganz abschalten. Ein echter Fund ist schon öffentlich: das Secret sofort rotieren.
- Für Agenten lesbar (README, „Für Agenten“): Jede öffentliche Seite mit eigenem Inhalt steht in `publicPages` in `apps/api/src/lib/public-pages.ts`, mit Titel, Beschreibung und ihrem Inhalt als Markdown in `body`, in der Sprache aus `m`. Daraus entstehen `/llms.txt`, `/llms-full.txt` und `<seite>.md`. Eine neue öffentliche Seite kommt im selben Zug dazu, der Browser-Test prüft, dass jede eingetragene Seite existiert. Hinein kommt nur, was jeder ohne Login sieht: nichts unter `routes/(app)`, keine Konten, keine Admin-Seiten, keine Links mit Token wie die geteilten Berichte unter `/r/<token>`. `publicPages` lädt bei jedem Aufruf alle Seiten: Bei Tausenden Einträgen die Abfrage auf das Wichtigste begrenzen oder eine Übersichtsseite pro Sammlung eintragen.
- Formatierung und Lint: Biome, Regeln in `biome.json`. `bun run format` behebt das meiste selbst.
- Strenges TypeScript, denn der Compiler ist die schnellste Rückmeldung: Die tsconfigs setzen `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride` und `noFallthroughCasesInSwitch`, Biome verbietet `any` (`noExplicitAny`, `noImplicitAnyLet`, `noEvolvingTypes`). Unbekanntes ist `unknown` und wird mit zod gelesen: Bodies per `validJson`, die Env per Schema in `apps/api/src/env.ts` (die Einstiege importieren es zuerst, eine neue Variable mit Pflichtwert oder Format kommt dazu), Antworten fremder APIs wie der Wallets im Runner per `safeParse`. Optionale Felder in Schemas, die an Bibliothekstypen gehen, mit `.exactOptional()`. Ein `switch` über eine Union endet mit `default: { const unhandled: never = value; throw new Error(String(unhandled)); }`. Typfehler an der Ursache beheben, nicht mit `as`, `@ts-expect-error` oder `biome-ignore` überdecken; `!` nur, wo der Wert sicher da ist (etwa nach `insert … returning`).

## Abweichungen vom Standard

- Das Overlay (`packages/sdk`) liest Antworten der API und den `sessionStorage` ohne zod, denn es läuft ohne Abhängigkeiten in fremden Prototypen. Die Typen dort sind Annahmen über die eigene API, nicht geprüft.
